Verified each area the owner named, catching two real, corrected
mistakes a naive proposal would likely make:

1. A bare `New-Service -BinaryPathName "python.exe serve.py"`
   registration does NOT work for a plain Python script — Windows
   Services must speak the Service Control Manager (SCM) protocol,
   which a console-mode Python process invoked this way never does.
   Corrected to a Scheduled Task (`AtStartup` trigger, `SYSTEM`
   principal via `-LogonType ServiceAccount`, zero new dependency) for
   `pwa/serve.py`, while `cloudflared` uses its own native, correct
   SCM integration (`cloudflared.exe service install`) — the two
   components are not interchangeable and were not treated as such.
2. `New-ScheduledTaskSettingsSet`'s `-ExecutionTimeLimit` defaults to
   72 hours, after which Task Scheduler force-kills the task even if
   healthy — for a server meant to run indefinitely this must be
   overridden to `[TimeSpan]::Zero`, or the PWA origin would
   mysteriously die exactly 3 days after every boot; the draft script
   does this explicitly.

Also verified and addressed: repo path and Python interpreter path are
unknowable from this environment and must fail closed (not guessed) if
wrong; `SYSTEM`-account `ServiceAccount` logon avoids ever storing a
Windows account password just to run without interactive login;
localhost-only binding (`127.0.0.1:8000`, no `--bind`/`--port` args)
preserved unchanged; the real Cloudflare tunnel token is deliberately
