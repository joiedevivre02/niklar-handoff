DECISION_REQUIRED: How does Niklar connect to Google Drive/Sheets,
Slack, and market-data evidence, and with what credentials — for both
(a) the orchestrator's 13 stage handlers (`authority_load` through
`postflight_verification`, currently unimplemented) and (b) a live
data source for the PWA (currently reads static synthetic JSON only).
Both depend on the same integration decision per
`docs/app/NIKLAR_APP_CONTRACT.md` "Held user decision."

OPTIONS:
A. GitHub Actions cron — orchestrator runs on a schedule in the
   private niklar-stocks repo; Google service-account key + Slack
   token as repo secrets (same pattern as GEMINI_API_KEY).
B. Local, Mac-driven — pipeline runs as local scripts; credentials
   stay in local keychain/.env, never touch any repo or cloud service.
C. Small private live API — an always-on private service holds
   credentials, runs the pipeline, and serves the PWA live data
   directly, replacing the static JSON entirely.
D. Stay synthetic — defer entirely; no live credentials introduced yet.

CLAUDE_RECOMMENDATION: Option A. Reuses a trust model already proven
safe in this exact repo (GEMINI_API_KEY via Actions secrets); ~$0 at
this scale; keeps credential surface no larger than needed; doesn't
foreclose C later (mobile_contract.py's transform layer is unaffected
by which option is chosen).

TRADEOFFS:
- A: Runs even when the Mac is off (fresher than B). Still needs a
  small complementary answer for how the PWA fetches the
  freshly-generated JSON (minimal private static host, or manual
  sync) — not yet solved, flagged honestly rather than assumed away.
- B: Most literal reading of "private-only" (credentials never leave a
  machine the user controls). Only fresh when the Mac runs a job;
  iPhone access needs same-network or a private VPN (e.g. Tailscale).
- C: Best "instant, from-anywhere, always-current" iPhone experience —
  the exact gap pwa/README.md already names as "Future (not
  implemented)." First genuinely internet-reachable component this
  system would have, even if access-controlled.
- D: Zero risk/cost, but the system's live value stays unrealized.

COST_COMPLEXITY: A: ~$0 (private-repo Action minutes), lowest new
infra of the "go live" options. B: lowest of all four, zero new
infra. C: highest — real hosting cost + ongoing uptime/patching/secret
rotation. D: zero.

CREDENTIALS_SECURITY: A: Google service-account JSON + Slack bot token
as GitHub Actions secrets — same trust model as GEMINI_API_KEY. B:
credentials in local keychain/.env only, never in any repo. C: held by
a persistently-running service — materially larger blast radius than
A/B if that host is ever compromised. D: no new credentials at all.

MOBILE_PRACTICALITY: A: fresh on schedule regardless of Mac state;
phone-side delivery still needs a small complementary piece. B: needs
same-network or VPN access from the phone. C: best — direct,
always-current, from anywhere. D: unchanged (synthetic data only).

INTEGRATIONS: All three "go live" options (A/B/C) give the same
direct read/write access to Drive/Sheets and Slack via the same
credential types — differs only in where that code executes and how
it's triggered, not in what it can reach. Market-data/evidence
acquisition (PSE EDGE + "fresh web search" per the manifests) is a
research task, not a market-data API call, under every option — this
decision does not change how that evidence gets gathered, only how
gathered/downstream state flows through Drive/Sheets/Slack/Master
Database.

REVERSIBILITY: A<->B: low risk either direction — same pipeline code,
only execution location and credential injection differ. Moving from
A or B to C later: low-medium — mobile_contract.py's transform layer
is unaffected, only a serving/auth layer is added. Starting with C
first: highest risk to unwind (existing API surface, auth scheme, and
hosting to decommission if the user later wants to step back).
